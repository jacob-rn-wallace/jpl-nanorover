# Render jobs (the hand-off between the modelling session and the render session)

**How this works.** Two machines share this repository. The **modelling session** (the desktop, an HP EliteDesk with no GPU) changes the CAD and the render scripts, commits and pushes. The **render session** (the owner's MacBook Air, M2, 16 GB) pulls, renders the jobs that are `pending` below, checks the images, marks the jobs `done`, commits and pushes. The render session does not change the models, the scripts or the docs other than this file and the images. If something looks wrong in a render, it records that in the job's row and leaves the fix to the modelling session.

## The automatic way (added 2026-11-14): one command on the render machine, no session needed

```
git pull
python3 hardware/assembly/render_pending.py          # or, with the repository's venv: .venv/bin/python hardware/assembly/render_pending.py
```

The script pulls, reads the Jobs table below, renders every row whose Status starts with `pending` (Blender headless, the Metal GPU on a Mac, the settings from the row's Settings cell), checks that each image exists and is not blank, sets the row to `done <date>` with the device and the time in Notes, commits the images and this file and pushes (with a pull and retry if the push is refused). A job that fails stays `pending` with the error in Notes. Options: `--dry-run` (show the jobs and stop), `--jobs R1,R2` (render these whatever their status), `--no-push`, `--no-commit`; see the top of the script. **It cannot look at the pictures: open the new images in `docs/images/` afterwards, and if one is wrong set its row back to `pending` with a note.** The Mac needs Blender 4.5.9 installed and, for the meshes, the repository's `.venv` (the script regenerates the strut and wheel meshes from it); both are described in `docs/blender-render.md`. A render session of Claude Code is still possible (below) for anything the script cannot do, such as fixing a scene problem.

## For a Claude render session: what to do

1. `git pull`. Read this file and `docs/blender-render.md` ("Setup on an Apple Silicon Mac", not yet tried: if a step there fails, note it under "Notes from the render session" below).
2. Make sure Blender 4.5.9 and the two meshes (`hardware/assembly/out/blender/struts.stl`, `wheels.stl`; git-ignored) are in place.
3. Render the pending jobs: `hardware/assembly/render_all.sh` (every job) or `hardware/assembly/render_all.sh R6 R7` (just those). It prints the device and the time of each job.
4. **Look at each image** before committing it (open the PNG): check that nothing is missing, black, blown out or in the wrong place; compare with the "expected" column.
5. In the table, set `Status` to `done YYYY-MM-DD` and put the render time in the `Notes` column; if an image is wrong, leave the job `pending` and say what is wrong.
6. `git add docs/images docs/render-jobs.md && git commit && git push` (the commit message names the jobs, for example "Renders R1 to R7 on the M2 (Metal)").

## For the modelling session: what to do

When a change to the CAD, the layout, the materials or the camera alters what a render shows, set the affected jobs to `pending` (with the reason in `Why`) and add a job here and in `hardware/assembly/render_all.sh` if a new view is needed. Commit and push, then tell the owner the render session has work.

## Notes from the render session

- 2026-11-14 (M2 MacBook Air): the Mac's existing `/Applications/Blender.app` was 4.1.1, which fails on the Principled BSDF "Thin Film Thickness" input (added in 4.2). Installed 4.5.9 LTS beside it (dmg SHA-256 matched `e3a3d7aa...`; copied to `~/tools/Blender-4.5.9.app`, not into /Applications) and ran with `BLENDER=$HOME/tools/Blender-4.5.9.app/Contents/MacOS/Blender hardware/assembly/render_all.sh`. `render_all.sh` picks `/Applications/Blender.app` by default, so on this Mac that variable must be set (or 4.5.9 put in /Applications).
- The venv existed, so `blender_export.py` regenerated `struts.stl` and `wheels.stl` from the STEP files without the CAD chain.
- Device reported: `METAL ['Apple M2 (GPU - 10 cores)']`. All seven jobs done; every image was opened and checked against "Expected". R6 was redone (it was the desktop's CPU test, 457 s there; 81 s here).
- 2026-11-14 (second batch, M2): pulled, regenerated the STL meshes (struts changed), rendered R1, R4, R6, R7, R9, R11 and redid R8 and R10 at 96 samples; all on Metal, 41 to 60 s each. Every image looked at: bare-aluminium bezel flush with the carbon, six hex-socket screws, window visibly recessed, six LEDs when lit (R7). Black bezel (R8, R9): ring and screws nearly vanish against the carbon. Gunmetal (R10, R11): reads as metal, screws visible. Nothing wrong found.
- 2026-11-14 (third batch, M2): pulled; rendered R1 to R7 and R10 with the gunmetal bezel as the default (45 to 62 s each, Metal). Looked at every image: gunmetal ring and screws read as metal against the carbon in the hero, detail, window and lit views; R10 (bare) shows the light aluminium ring; the rear, top and cells views are unchanged apart from noise. Nothing wrong found. Note: `rover-window-gunmetal.png` and `rover-detail-gunmetal.png` from the earlier batch are no longer produced by any job (gunmetal is now the default, R6 and R4) and are left in `docs/images/` for you to keep or delete.
- 2026-11-14 (the owner's first run of `render_pending.py` on the Mac): both jobs failed with `KeyError: ... "Thin Film Thickness" not found`: the script had picked `/Applications/Blender.app`, which is 4.1.1 (the thin-film input arrived in 4.2). Fixed in the script (with the render session's advice on the Mac's setup): `blender_binary()` now tries `$BLENDER`, `~/tools/Blender-4.5.9.app`, `/Applications/Blender.app`, then the Linux tarball, runs `--version` on each and takes the first that is 4.2 or newer, prints it, and otherwise stops with the 4.5.9 dmg URL and SHA-256; it never falls back to an older Blender. The failure note is now the last real error line in full (no `|`, cut near 200 characters), and **failure notes are committed and pushed** (a repeat of the same failure changes nothing and makes no commit). The line `'Scene' object has no attribute 'vs'` in Blender's output comes from an add-on in the Mac's Blender preferences and is harmless; the script ignores it. `blender_render.py` is unchanged.
